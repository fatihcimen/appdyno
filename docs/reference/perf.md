# Performance measurement

[Türkçe](perf.tr.md)

Every measurement is read from the platform's own tools and stored with the raw output it came from
(`<measurements dir>/pm-<id>.json` and `.txt`; the MCP server's `--measurements`, default
`~/Library/Caches/appdyno/measurements`). Commands run in the C locale. Nothing leaves the machine.

Words this page uses. The **fixture** is this project's own test app (`dev.appdyno.fixture`), which can add a known cost, such as 500 ms at its start, so that a measure can be checked against it. **Host load** is the Mac's 1-minute load average, on 15 cores unless said otherwise. The **probe** is a small library put into a simulator app to time its frames ([below](#the-simulators-frame-probe)). A **kind** is the name a number is kept under, such as `launch.ttid_ms`. The gate **calls** a change when it judges the change real. A **hang** is a time in which the app's main thread did not answer; a **frozen frame** is one frame of 700 ms or longer.

What each measure read against a known cost, on which device and at what load, is in [How the measures were validated](perf-evidence.md).

## A Baseline Profile

`perf_launch` with `baselineProfile: true`, on a build that is not debuggable: a debuggable app stays at `verify` whatever is asked, and is refused. On a cold start it says three things.

| what     | read from                                                                    | what to know                                                                                                                                                                                                                                          |
| -------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| present  | `assets/dexopt/baseline.prof` in the installed APK, `unzip -l` on the device | no profile, no more is done                                                                                                                                                                                                                           |
| applied  | `status` in `dumpsys package dexopt`                                         | not `reason`: a `.dm` for another range of API installs with no word and reads `status=verify reason=install-dm`, and the answer calls it delivered with nothing compiled; Android 17 refuses its install. A build's folder holds one `.dm` per range |
| worth it | cold starts at `verify` and at `speed-profile`, in 3 turns of `repeats` each | the profile goes in by ProfileInstaller's broadcast, which `result=1` confirms, and each turn's status is read. `pm dump-profiles` gives its rules from API 34                                                                                        |

The starts with and without the profile take turns, so that the Mac's drift falls on both, and a change is called on the rank test and the floor of [the gate](#the-gate). The profile goes in again before each turn, and an app with neither ProfileInstaller nor a `.dm` is refused rather than timed with nothing compiled. The app ends as an install leaves it, and a profile it gathered in use goes with that. The two numbers are kept as `launch.without_profile_ms` and `launch.with_profile_ms`, under the scenario `launch-baseline-profile`. What a phone gains has not been measured: ProfileInstaller refused the only phone tried.

How this was checked, and on which devices: [the evidence](perf-evidence.md#a-baseline-profile).

## The gate

Every measure's numbers are kept as records (`packages/perf`): kind, median, samples and spread, source command, raw output
file, device and OS, virtual or physical, build type, compile state, host and device load, thermal state, tool version and
time. A run goes to `<measurements dir>/runs/<app>/<scenario>/<device class>/`. A baseline goes to
`.appdyno/perf/baselines/<app>/<scenario>/<device class>.json` (`APPDYNO_PERF_DIR` moves it), which can be committed. Limits
go in `.appdyno/perf/budgets.json`: a list of `{ "kind": "launch.ttid_ms", "max": 2000 }`, with `app`, `scenario`, `deviceClass`
and `min` optional. `perf_compare` `budget` with `kind` and `max` or `min` writes one there, in place of a rule of the same kind and scope, and needs no run measured (`appdyno perf budget --app A --kind launch.ttid_ms --max 200`). A kind no measure keeps is refused, with the kinds of that name it may have meant. A kind none of the app's kept runs holds is kept all the same, and the answer says so and names the kinds they hold.

| command                                                     | what it does                                                                                                    |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `appdyno perf-launch --app A --mode cold --repeats 6`       | measures a run and keeps it                                                                                     |
| `appdyno perf baseline --app A [--last 3]`                  | adds the newest run, or runs, to the baseline, each once; exits 1 until it holds 3 runs and 5 samples of a kind |
| `appdyno perf compare --app A [--format text\|json\|junit]` | exits 1 on a regression, a broken budget, or a change it could not judge                                        |
| `appdyno perf budget --app A`                               | checks the budgets only                                                                                         |
| `appdyno perf why --app A`                                  | does what `compare` does, and on a regression looks for its cause                                               |

The tool `perf_compare` does what the last four do, its `action` naming which: `baseline`, `compare`, `budget` or `why`. [Why it got worse](#why-it-got-worse) says what `perf why` runs.

**How a change is called.** A number that did not move past its floor is `ok`. The floor is the largest of a floor by unit (15 % and 10 ms for times) and 4 standard deviations of the baseline's run medians. Past the floor, the gate needs 3 baseline runs and at least 5 samples on each side, else `few-samples`: a change it could not judge, which is no pass and exits 1. Then a rank test of all the baseline's samples against the run must give p under 0.01 (by permutation, as whole milliseconds tie; 4 against 4 cannot reach it). A better change the test confirms is an `improvement`; a better one it does not confirm, or a worse one at p 0.05 or more, is `ok`. A worse change at p from 0.01 to 0.05 is `noisy` and exits 1: measure again with more repeats, as a few slow samples on either side hide a real change from the test (on a simulator, 600 ms put into the start read +754 ms past a floor of 415 ms with p 0.033, against a baseline with launches of 6.4 and 3.9 s, which the test alone would have passed). A worse change the test confirms, in a run or against a baseline measured under high load, on a hot device or with a mirror open, is `noisy` too and exits 1, as the gate cannot tell the change from the load; any other is a `regression`, and exits 1. A kind every run of a baseline of 3 or more holds and this run lacks is `few-samples` too, as a screen that stops drawing keeps no frames: changing a flow's steps stops its gate until the baseline is taken again.

**What load keeps out of a baseline.** A number measured with host load over 0.8 a core (on a virtual device, or a number timed through this Mac), on a busy or hot device, or with a mirror open, is left out of a baseline and named, and the rest of its run goes in; a run with nothing else is refused as a baseline. On a Mac that is itself a virtual machine, as a CI runner is, the load average says nothing of how busy it is (a GitHub runner of 3 cores read 115 to 650 at rest), so it is not read: the number says `host-load-unread`, which stops nothing and keeps nothing out, and the gate's own tests judge the noise. `APPDYNO_HOST_VIRTUAL=0` reads it on a virtual Mac all the same. A run whose build or compile state differs from its baseline's is `refused` and exits 1, naming both sides. A number with no baseline is `new`, and passes where its scenario has a baseline, as a step put in does; a scenario with neither a baseline nor a budget was judged by nothing, and exits 1. A phone whose load, pressure, share at work and heat could not be read says `device-state-unread` beside its numbers: that stops nothing and keeps nothing out of a baseline, but a device unread is not a device known to be calm. A virtual device's state is this Mac's, which is read.

How this was checked, and on which devices: [the evidence](perf-evidence.md#the-gate).

## Kept traces

Traces and heap dumps stay on this machine, up to a limit: 10 GB by default, `--trace-limit-gb` or `APPDYNO_TRACE_LIMIT_GB` to change it. `appdyno perf prune [--limit-gb N] [--dry-run]` or `perf_compare` `action: prune` brings them down to it and lists what it removed; a dry run lists the same and touches nothing. Each removal goes in `traces-pruned.log` in the state folder, with its time and size. A simulator's frame probe reads are counted with them. The server and the command line also look when a run or a measurement is kept, or the flight recorder saves a page, at most once an hour. Nothing else that makes a context does: not the library, and not a test.

They go oldest first, and never what a baseline took its numbers from, what one of a scenario's 30 newest runs names, or what is under a day old, so it can stay over the limit, and says so. A baseline holds samples and no path, so the way there is the baseline's run time to the kept run, the run to its measurement, and the measurement's two files to the trace. Taking a baseline also pins what it took, in `traces-pinned.json`, as one project cannot see another's baselines.

**What it does not know, it does not delete.** It goes by one state folder: it reads that folder's `measurements`, and removes only direct entries of that folder's `traces` and `measurements` that are traces or heap dumps. With no kept run to go by, or a run, a measurement, a baseline or the pins it cannot read, it removes nothing and says why. A context with `--measurements` elsewhere is refused: the traces are not its runs' to speak for. A link is not followed, and a linked `traces` folder stops it.

## Why a slow frame was slow

On Android, `perf_trace` records what each frame's main thread did and answers for the frames that missed their deadline (`android_frame_stats`, `overrun` over 0): how long a frame it spent waiting for a monitor (`android_monitor_contention`), in binder calls (`android_binder_txns`), waiting for the collector (`GC: Wait For Completion`), and from `thread_state` at work, waiting for a CPU, blocked in the kernel or asleep with nothing named holding it. A wait is also a sleep, so it is taken out of the sleep. One is named only at 10 ms a frame or more and 40 % of the time or more; otherwise the frames are unexplained, which is said, not guessed at. The window is the frame's `doFrame`, so a stall before it began, or on the render thread, reads as unexplained.

How this was checked, and on which devices: [the evidence](perf-evidence.md#why-a-slow-frame-was-slow).

## Why a hang was a hang, and which function moved

**iPhone, busy or blocked.** `perf_trace` `what: hangs` answers each hang as Apple triages it. A Time Profiler trace holds no `thread-state` table on a phone, but it samples only a thread that runs, so the hung thread's samples inside a hang are how much of it was on the CPU: at half or more it was busy, in what ran most, and below that blocked, in what it ran last. Nothing new is recorded. The function is the app's innermost, an address where the build has no symbols, and `dsym` on `perf_trace` or `perf_profile` names it. Of a blocked thread the last sample may be thin: a Release build's closure has read as `main`.

`dsym`, a `.dSYM` or a folder of them, names frames with `atos`, from the addresses and the load address the export has, and refuses a dSYM of no build in the trace. It names what is read, not the trace on disk: `perf_query` still sees addresses. A `perf_profile` given no `dsym` whose app functions are all addresses says so, and what makes the dSYM: `DEBUG_INFORMATION_FORMAT` set to `dwarf-with-dsym`, a Release build's default and not a Debug build's, which leaves it beside the `.app` in its build folder or in its archive.

**A function-level diff.** `perf_compare` `action: functions` with two ids of `perf_profile`, or `appdyno perf functions --from pm-a --to pm-b`: what moved, in ms of CPU in each second so that windows of other lengths compare, the app's own functions where the profile has them. A function must move 20 ms a second and a quarter of itself, so two runs of the same work name nothing. A profile keeps 200 functions, and an answer shows 15. Android's names are what simpleperf finds on the device: Java functions of a debuggable build, once compiled, and the first run of a screen may read as the interpreter.

How this was checked, and on which devices: [the evidence](perf-evidence.md#why-a-hang-was-a-hang-and-which-function-moved).

## Why it got worse

`appdyno perf why` is the gate, and on a regression it looks for the cause by itself, on the same device, the same build and the same journey, and writes one answer: what got worse and by how much, how sure the gate is, against which baseline and which run, and the likeliest cause with what shows it. The same comes through `perf_compare` with `action: why`, in `answers`, and on the dashboard. It fails as `perf compare` does: exit 1 on a regression or a broken budget.

| command                                                                 | what it does                                                  |
| ----------------------------------------------------------------------- | ------------------------------------------------------------- |
| `appdyno perf reference --app A [--scenario S] [--device S] [--dsym D]` | on the baseline's build, keeps the other side of a later diff |
| `appdyno perf why --app A [--scenario S] [--device S] [--dsym D]`       | the gate, and on a regression its cause                       |
| `appdyno perf comment --app A --out comment.md`                         | writes the answers to a file as Markdown; needs no device     |

**Only a regression is looked at.** Every call is the gate's own, with its rank test, floors and run-to-run limit. A run with no regression touches no device, and `noisy`, `few-samples` and `refused` are said and nothing runs: noise is not a regression. What a look reads is kept as a measurement and never as a run, so it cannot become the newest run the gate compares.

**A look leaves the device as it found it.** A look can bring up a simulator's runner, and with one up the same `assert` read from 11 ms to 39 ms, as a read then goes another way: a first version had the gate rightly call that on the next run of an unchanged app. So a look stops what it started, and a runner that was up before it stays up.

**What runs, by the number that moved.**

| number                                 | what runs                                                                         | what it can name                                     |
| -------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------- |
| a start                                | one traced start, as `perf_launch` `trace`                                        | the phase that rose, against the reference           |
| a journey's step                       | the flow replayed, a first time left out, with a recording around that step alone | the function that rose, and what the main thread did |
| frames, frozen frames, stalls          | the swipes the run did, recorded twice: a CPU profile, and a frame or hang trace  | the same                                             |
| CPU                                    | a CPU profile of what the app does                                                | the function that rose                               |
| memory, network, energy and the others | nothing                                                                           | that no measure here explains it                     |

A journey's whole goes with the step that moved most. A step that starts the app is looked at as a start, and in a step that stops it the app does not run, which is said.

**Why a reference.** A function diff needs both builds, and once a regression is there only one is installed. `perf reference`, with the baseline's build installed, keeps a CPU profile of each step of the journey and the phases of a start in `.appdyno/perf/references/`, beside the baseline, so that it can be committed. One of another build type or compile state is not used, and the answer says so. With none, the answer says what it would take; what needs no other side, a frame's cause or a hang's, is still read.

**A cause is named only with what shows it.**

- A function, by the same diff as `perf_compare` `functions`, in ms of CPU in the step: it must pass the diff's floors and account for 40 % of the change or more, the bar a frame's cause is held to. Below that it is evidence, and no cause is named.
- A profile that counts callers in, as a simulator's does, has a caller rise as far as what it called, so `main` rises with everything. Of those that rose about as far, the deepest is named.
- A phase by the gate's floor for a time, and the same 40 %.
- A frame's cause and a hang are read straight from the run's trace: [why a slow frame was slow](#why-a-slow-frame-was-slow).
- A profile sees what is on the CPU, and a frame trace what the main thread did in its frames. A sleep in a touch's handler holds up no frame in flight, so it shows in neither, as a timer or a wait for the network does not: the answer says no cause was found and why, not the nearest thing that moved.
- If the change does not show again while it is looked at, that is said: what was read may not be that change.

**On a phone** the gate goes by the phone. What the phone timed itself is called whatever the Mac is doing, and what was timed on the Mac is left out of a baseline by name. If the gate could judge the numbers the phone timed itself, a change in a number timed on a loaded Mac is only a note and fails nothing. If it could judge none of the phone's own numbers, that change fails the run as `noisy`, as it does on any device. On an iPhone `perf_launch` is timed on the Mac, so a loaded Mac refuses the run whole; with `trace: true` its phases are the phone's own, one sample a run. A phone that is hot, or busy, is refused: that is the phone's own state, and the gate is right. On a phone a function is an address unless `--dsym` names the build's dSYM, on `perf reference` and on `perf why`. On an iPhone a hang trace sees a wait too, so a sleep in a touch reads as a blocked hang, in what ran last, and not as no cause.

**How sure.** The gate's own numbers beside each answer: p, the samples on each side, the baseline's runs, and how many times its floor the change is. A modelled number stays `(modelled)` and one timed on this Mac `(timed through the host)` on every surface, and a virtual device's answer says what the dashboard says of one.

**A replay's values** come from the environment. A value given by `--param` is not kept, as it may be a secret, so a flow that needs one has it set, or the answer says which it lacks. A flow changed so that a step is no longer that step is said, and not timed.

**The comment.** `perf comment` reads what `perf why` kept of the newest run of each scenario, and an answer of an older run is not used. All that comes from the app is escaped, as a pull request can name a function anything and an `@name` would notify someone. A body is cut at 60,000 characters. [`perf-gate.yml`](../examples/perf-gate.yml) is a job to copy: see [On a pull request](../guides/performance.md#on-a-pull-request).

How this was checked, and on which devices: [the evidence](perf-evidence.md#why-it-got-worse).

## Why an app started

On Android 15 and later, `perf_snapshot` with `also: startInfo` reads `dumpsys activity start-info`, with no trace: the reason of the newest start, its type, whether it followed a force stop, and where its time went, for the starts the system keeps. Each phase of a start since the last run of the key also goes to the row "Why launch was slow", as the system keeps a start for as long as it likes. The first run to read a start keeps no phase of it, as nothing says it is new. The time inside `Application.onCreate` is in `oncreate_to_first_frame`, not before it. Before Android 15 the measure is listed as not measurable, with the reason kept. Reading it needs the app running, as `perf_snapshot` does: a process up for a broadcast counts, and reads 0 frames.

How this was checked, and on which devices: [the evidence](perf-evidence.md#why-an-app-started).

## A journey

`appdyno test <flow> --measure` or `flow` `run` with `iterations`. A first run is left out, as a measured launch leaves out its warm-up, and the iterations (5 by default: the gate calls nothing under 5 samples a side) make one kept run of the scenario `journey-<path>`, the file's path in its repository with `-` for each `/`:

| kind                                                   | what                                                                                                                                                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `journey.total_ms`                                     | each iteration's steps added up                                                                                                                                                                   |
| `journey.<n>_<line>.ms`                                | the device's own count from the action to a settled screen; `launch`, `open_link`, `scroll_to`, `wait_for`, `assert` and what has no such count are the action on this Mac's clock, `throughHost` |
| `journey.<n>_<line>.frames_p95_ms`, `.frames_worst_ms` | the step's frames: reset before its action, read after it settled; none when it drew nothing                                                                                                      |
| `journey.<n>_<line>.memory_kb`                         | what `perf_snapshot` reads, after it settled                                                                                                                                                      |
| `journey.unsettled`                                    | how many of an iteration's steps never settled: such a step keeps no time and its iteration no whole, as the tool's deadline ended it; its frames and memory are read at that deadline            |

The reads are between the steps, so they cost time but are in no step's number. A step after which the app does not run has no reading, and the run goes on.

**A measure inside a flow.** A `perf_*` call during a recording used to be written as `unrecorded`, which stopped the replay. A measure is the agent measuring, not the journey, and a journey now has its numbers from `--measure`, so what it did to the screen stays as the plain steps that do the same and nothing stops: `perf_launch` cold is `stop`, `launch`, warm or hot is `launch`; `perf_scroll` is its swipes; `perf_trace` or `perf_profile` with `scroll` is 4 swipes; XCTest's own test is `stop`, `launch`. What leaves the screen as it found it writes nothing, and so does a call refused after the probe's relaunch.

How this was checked, and on which devices: [the evidence](perf-evidence.md#a-journey).

## One timeline

A timeline puts what happened in a journey on one clock, in one HTML file: the video, touches, steps, frames, requests, traffic, the log and memory. Click a slow frame and the video goes to that moment, with the requests and the log lines around it. The file opens with no server and no network, and can be sent to someone.

```sh
appdyno timeline --app com.example.app --flow journey.flow    # a flow, or --seconds 30 of your own hands
```

Through the server: `report` `timeline`, then the journey, then `report` `stop`; a session's end writes it too. A timeline lasts at most 180 s, as past one recording's segment the video's own times are lost. It writes `timeline.html` beside the report, and a video over 64 MB stays beside the page, with the page saying so. A `perf_*` run during it is marked `mirrored`, as an encoder is at work on the device. Its frames each second are what the counters grew by, as a reset would cut the window a `perf_scroll` counts from its own: one that reset them every second left a list janking on every frame at 0 % on an Android 14 emulator, against 97 % alone, and now reads 98 %; on a simulator it left 0 frames, and now 100 % as alone. The second in which another measure begins its own count has no frames.

### One clock

Everything stands on the device's own clock. What was read there needs nothing done to it, and what was read on the Mac is moved by an offset that is measured at both ends of the run and never assumed: an emulator's clock read 25 to 31 ms ahead of this Mac, an iPhone's 2 ± 1 ms, a simulator's 0 ± 1 ms. The offset comes from the agent's `ping`, answered past the queue: the shortest round trip of eight, half of it the bound, and a millisecond for `Date.now()`'s own tick. It has to be the shortest: of 24 reads of `adb shell date` under load, one was 254 ms out.

The page says how far off each row can be, and two rows can be apart by at most the sum of their figures:

| row               | read on | placed by                                                          | within       |
| ----------------- | ------- | ------------------------------------------------------------------ | ------------ |
| Video, Android    | device  | each frame's own time, in the metadata track `screenrecord` writes | ±40 ms       |
| Video, simulator  | Mac     | when its recording began, as measured of this recorder             | ±150 ms      |
| Video, iPhone     | Mac     | when its stream began, as measured: it has no steady lead          | ±620 ms      |
| Frames, touches   | device  | the trace's own clock snapshots (`to_realtime`)                    | ±1 ms        |
| Frames, simulator | Mac     | the probe, which reads the wall clock                              | ±1 ms        |
| Frames, iPhone    | device  | the date their trace began                                         | ±215 ms      |
| Log               | device  | the time on each line                                              | ±1 ms        |
| Steps, requests   | Mac     | the offset                                                         | about 1.5 ms |
| Memory, traffic   | Mac     | the offset, and a reading is taken somewhere in its second         | ±1 s         |

### A stall no frame shows

Android's frames are blind to one common stall. A main thread held up in a click, with a ripple drawing on the render thread, drew no long frame in Perfetto's timeline: a 1500 ms hold read a longest frame of 27 to 38 ms on an emulator, 59 on a Xiaomi and 64 on a Samsung. The frame timeline has no row of it either, by actual or by expected time. `gfxinfo` read 21 ms on the emulator, and on the Xiaomi 1525 ms in one run of two, so it cannot be gone by. What says so is Choreographer's own line in the app's log, `Skipped 90 frames!`, at the moment the thread came back: 90 × 16.7 ms is the 1500 ms put in.

So the page takes those lines as its Stalls row, 1483 ms on the emulator and 1499 on the Xiaomi, by the refresh its frames show, and leaves out one a long frame already shows: one stop is one row. `perf_trace` does the same: `stalls.worst_ms` is the longest frame or the longest such hold, whichever is more, and its answer has `heldMs` and says the number came from that line. The flight recorder watches for it too.

**Where this does not reach.** A Samsung with One UI writes no such line: none in the log of a run with that same hold, whose `Taps: 1` shows it ran. There such a hold shows nowhere, and the page says so. The line comes only past 30 frames skipped, so a shorter hold shows nowhere on any device. `perf_scroll` goes by what it reads while it scrolls, which is driven by the main thread, and does not read this line.

### What each device gives

| row      | Android                                        | iOS simulator                            | iPhone                                           |
| -------- | ---------------------------------------------- | ---------------------------------------- | ------------------------------------------------ |
| Video    | yes, each frame stamped                        | yes, placed within 150 ms                | yes, HEVC, placed within 620 ms                  |
| Frames   | yes: every frame, with Perfetto's verdict      | yes: the probe, which relaunches the app | its hitches and hangs only, placed within 215 ms |
| Stalls   | by the log's Skipped frames, but not on One UI | a long frame shows them                  | a hang shows them                                |
| Touches  | yes: what reached the app, from anyone         | no: Steps are what this tool sent        | no: the same                                     |
| Requests | through a proxy capture                        | through the probe or a proxy capture     | through a proxy capture                          |
| Log      | yes                                            | yes                                      | no: `devicectl` cannot read a running app's log  |
| Memory   | yes, every 5 s                                 | yes                                      | by its own instruments                           |

A row a device cannot give stands empty, with the reason its device gave. Android was run on an emulator (Android 14), a Xiaomi (Android 16) and a Samsung A52 (Android 14); the iPhone is a 13 Pro Max.

### What the file holds

The page says this at its top: it gets sent to people.

- The screen, as a video. It is not painted over: what was on the screen is in the file, a password field's dots and all.
- The app's log lines, with listed secrets and what looks like a credential hidden. That hiding goes by patterns, so a person's name or an address in a line stays. Read them before you send it.
- Requests by method, host and path. No query, which is where a token rides, and no body: this tool keeps none. A path can hold an id. `--full-urls`, or `APPDYNO_FULL_URLS=1`, keeps the query, with a credential in it still hidden. It is a flag of the person who starts the tool, and no argument an agent can pass.
- Steps by name: no text that was typed.

The page's one script is allowed by its hash, so a second script on it does not run, whatever a log line holds: tried in Chrome. The video goes inside as base64, read by that script into a blob. Chrome played an MP4, a simulator's QuickTime file and an iPhone's HEVC so, and went to the moment asked. Safari has not been tried.

### The flight recorder

```sh
appdyno flight --app com.example.app --seconds 30    # until Ctrl-C; through the server, report flight, report stop
```

It keeps the last N seconds of an app as a timeline, 30 by default, from 20 to 120 (`--flight-seconds`, `APPDYNO_FLIGHT_SECONDS`), and saves them when the app crashes or stalls. It is off until a person turns it on, and it ends with its session.

**What sets it off.** The signals the measures read: a frame of 700 ms or more or a frozen frame, a stop of a main thread in its log, and a process gone with a crash report. It looks every 5 s, as a look costs the device and nothing is lost by waiting: the ring holds the moment, a frozen frame stays counted until it is read, and a log and a crash report stay. A look queues behind what the device is doing: they came 14 and 22 s apart on an emulator at host load 33 to 41, which is why it keeps no less than 20 s. It goes by the process, not by whether the app runs: Android restarts a crashed app within the second, and a look at `pidof` then finds one running. A process gone with no report is one a person closed, and nothing is kept. A stall is saved 2 s after, with the screen coming back, and one that repeats is one to look at: none is saved within N seconds of the last, and at most 20 in a run.

**What it holds, and where.** The frames in Perfetto's ring on the device, sized for N seconds. The video on this Mac in three overlapping segments of N/2 seconds at 1 Mbit/s, so nothing falls between two. A Samsung A52 runs one encoder: a second `screenrecord` makes its file and dies at the first frame, `Encoder failed (err=-38)`, however long it is given. There the old segment ends first, and what passes while the new one starts is not filmed; ending one took 0.6 to 0.9 s. An open window holds that encoder too, so a recording under one refuses at its start, in 0.7 to 0.9 s there, and the window goes on. Both are gone when it stops. A saved page goes in `traces/`, as `<app>-flight-<time>.timeline.html`, with the trace of that stretch beside it, and both go by the rules of [kept traces](#kept-traces): nothing under a day old goes, and past the limit the oldest go first. `report` `write` saves now. A session that starts after a process died clears what that process left on this Mac; what it left on the device ends by itself: in a run with its owner killed every `screenrecord` was gone within 45 s and Perfetto within its 10 minutes, and the next timeline removes the file Perfetto leaves.

**What it costs.** It looks at the device every 5 s, and it does cost something: it is for a run a person means to look at, and a `perf_*` run during it is marked `mirrored`. On a Xiaomi a look every 5 s took the phone's whole CPU about 9.5 points higher. What it holds on this Mac is at most three segments of N/2 seconds at 1 Mbit/s, so 5.6 MB for 30 s.

How this was checked, and on which devices: [the evidence](perf-evidence.md#one-timeline).

## A second recording, and an iPhone's heat

**Two recordings at once refuse by name.** Xcode's trace tool, given a second recording, fails to lock the performance counters and leaves an empty trace, so `recordTrace` holds a device across processes, and a second gets `DEVICE_CLAIMED` naming the first, a dead holder's file being taken over. On the iPhone the second refused and the first kept its trace. A recording by another tool shows only as that failure, which refuses the same way. Android's Perfetto takes sessions side by side, so it has no such rule.

**An iPhone's thermal state.** No tool answers this by itself, but every recording but a lone Power Profiler instrument holds `device-thermal-state-intervals`, so a measure reads the state its recording ended in, up to 5 minutes old, on Android's scale that a run's noise is judged by: nominal 0, fair 1, serious 2, critical 4. A measure with no recording in the last 5 minutes, such as a launch alone, has none. On the iPhone it read 0.

## The dashboard

| command                                                 | what it does                                                    |
| ------------------------------------------------------- | --------------------------------------------------------------- |
| `appdyno perf survey --app A [--device S]`              | runs every measure on that device in turn, then writes the page |
| `appdyno perf dashboard [--app A] [--out dir] [--open]` | writes the page alone, from what is kept; needs no device       |

`perf_compare` with `action: dashboard` writes the page too, in its usual place: `<measurements dir>/dashboard/index.html`. `--out` and `--open` are the command line's alone. The page is rewritten after each kept run and each baseline, and an open page reloads itself every minute, which closes a table left open. A failure to write it never fails a measurement.

`perf survey` calls the same operations anyone can, and names no device: what reads each measure is tried in turn until the measure has a number, a refusal is kept as that measure's answer for that app on that kind of device, and the next measure still runs. Every operation keeps its refusals the same way, except what the caller turned off (`probe: false`) and a way the device has another of (no `hangs` where the frame trace reads stalls); a refusal about a part of a row (threads, a CPU profile) stands for no row. A call that ran and kept no number for that measure, or failed for another reason such as a timeout, is printed and not kept: neither says what the device cannot do. One line per measure.

There is no server, and the page is one file with no script, which loads nothing: its content policy allows only its own style. Everything from the store is escaped. It follows the system's light or dark, and prints as ink on paper with no tooltips or tables. An app has a section of its own, with an anchor. In order:

1. **What needs attention**, across every app, for the newest run of each scenario: regressions and broken budgets as `perf compare` calls them, with the cause `perf why` named of that very run, and runs under high load or heat. An app with a regression opens with **Why it got worse**, the same answer the command line gives. A debuggable build is said beside its number but is no alarm. It says how many scenarios have a baseline and how many budget rules there are, since "nothing needs attention" means little without them, and which files could not be read.
2. **Measures by device.** The row `Journeys` holds the newest journey on that device, its whole time, its slowest step and the steps the gate calls slower. Above the table: that an emulator's or a simulator's numbers are relative to this Mac and that real frame rates, frozen frames, hitches and energy need a phone, and, with no phone measured for the app, the command for one. A cell holds the newest reading of that measure on that kind of device, with its unit, kind, scenario and age; an estimate from a model is marked; so is a reading under noise; and on a simulator it says when the number is something else: main-thread pacing for frames, frozen frames and stalls, this Mac's energy. A refusal newer than any reading gives its reason instead. Otherwise "not measured yet". A kind no measure answers has a row of its own under "other". Emulators and simulators read as relative, and the page says so.
3. **Trends**, for a kind with more than one run on a device: one small chart per kind, scenario and device, each with one y-scale, from zero, with the runs evenly spaced. The shaded band is the baseline's median plus and minus the floor of the gate above: a run outside it has moved past the floor, though the call needs the rank test as well. A budget is a thin dashed line straight across the chart, drawn when it is within twice the data's top, and named under the chart either way. A hollow point was taken under noise. Where any run of a chart is an estimate from a model, the line through the runs is itself dashed, and the chart is marked as an estimate. The newest launch phases (`launch.phase.*`) are one bar split into phases, up to six with the smallest folded into "other", and each journey's newest run one bar split by step, with a table of each step's time, verdict, frames and memory; a journey's whole has a trend, and so has a step the gate calls slower. Every chart has a table under it.
4. **An empty store** shows the one command that fills it.

A trend reads a key's newest 30 runs and says how many there are. Times are UTC.

How this was checked, and on which devices: [the evidence](perf-evidence.md#the-dashboard).

## Asking a kept trace

`perf_query` answers from a kept trace with no new recording: read-only SQL on a `.pftrace` through the pinned trace processor (optional
`INCLUDE PERFETTO MODULE` lines, then one `SELECT` or `WITH`), and on an Instruments `.trace` a table digested to its top rows (`table`; none
lists the tables). Rows are bounded, cells cut at 200 characters, and only files under the traces or measurements folders are read.

## The simulator's frame probe

On by default for `perf_scroll` and `perf_trace` on a simulator, and `probe: false` turns it off; `perf_launch` takes it on request, so that a kept launch stays one kind whatever else measured the app. `ios/SimHelper/SimProbe.m`, compiled on first use with clang (no binary ships), injected through `SIMCTL_CHILD_DYLD_INSERT_LIBRARIES`. The app relaunches once, unless it runs under the probe already; the app is not rebuilt. The relaunch leaves it on its first screen, so `perf_scroll` and `perf_trace` then measure nothing and refuse with `CHECK_FAILED`: open the screen again and call once more. They do not bring the app back where it was, as the way there is the app's own and no replay of it is sure: on the fixture a list opened by a link measured its first screen at 0.4 % and 3.1 % jank in two runs, where the list itself janks on every frame.

It runs a `CADisplayLink` on the main run loop and writes every frame interval, stalls over 100 ms, and when the app last finished handling a touch. Every result says what it is: main-thread pacing, not the render server or GPU, on the Mac's speed. It finds stalls and regressions on one machine; it does not predict a phone's frame rate, as [Apple says of simulators](https://developer.apple.com/documentation/xcode/running-your-app-on-simulated-or-physical-devices) that they do not replicate a device's performance.

A start through it (`perf_launch` with `trace`) writes its phases: `load`, process start to the library's first code; `main`, to UIKit's application object, so static initializers and what runs before `UIApplicationMain`, a SwiftUI app's `init` among them; `uikit`, to did finish launching; `first_frame`. A second start, held before its first instruction by `simctl launch --wait-for-debugger`, is profiled from there, and its busiest functions are in the answer.

## Against Play's definitions

A local run says "this session would count" or "would not", in the answer and on the dashboard, with the number and the limit beside it, and never a rate: Play's thresholds are shares of users or sessions over 28 days ([vitals overview](https://developer.android.com/topic/performance/vitals), [Play Console help](https://support.google.com/googleplay/android-developer/answer/9844486), [technical quality requirements](https://support.google.com/googleplay/android-developer/answer/17492799)), and one phone in one run has neither.

| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `frames.frozen_percent`, from the same, from 1,000 frames             | over 0.1 % take 700 ms or longer. A hot start's limit is 1.5 s by the developer page and 1 s by the help page; 1.5 s holds here, and the answer says the other. The help page is out of date on other points, such as wake locks, so it has the lesser claim. A bucket of the histogram holds a whole millisecond and those above it, so a frame of 16 to 17 ms is left out of "over 16 ms" and that share is the least it can be. At 90 or 120 Hz the same page speaks of a missed deadline too, and nothing settles which: 16 ms is Play's written number, and `frames.jank_percent` keeps the deadline's share beside it. An app with no View toolkit (Vulkan, a game engine) has no such frames, as Play says of it too.

**What a run keeps of how an app ended.** `exits.crashes`, `exits.anrs` and `exits.user_anrs` are what happened during the run, and never what the system still holds. A snapshot is a moment, so they count what is newer than the last run of the same app, scenario and kind of device, by the system's own stamps: each exit's and each dropbox entry's time on Android, read against the device's own clock as they are in its local time, and the time in each report on iOS. A first run has nothing to count from and keeps none. What the system holds, 16 exits, a dropbox with no age limit and up to 100 reports, is said beside it as `the system holds N`, and feeds no gate and no Play line. A run's time is stamped after its reads, so what falls between the two belongs to neither.

**How an app ended.** `crashes` reports what is a death, with its stack, and counts every exit the system keeps by its reason in full, so that an end nobody calls a crash is seen: `every exit kept: USER REQUESTED FORCE STOP 2, SIGNALED status 9 1, ...`.

**A surface's frames.** What a game or an engine draws goes to a `SurfaceView`, past the View toolkit, so `gfxinfo` has no frames of it: it read 6 for a surface that drew 78. `perf_snapshot` with `also: surface` reads the app's `SurfaceView` from `dumpsys SurfaceFlinger --latency`, which keeps a surface's last 127 frames whatever their age, so it says how long ago the last one was. A present lands on the display's refresh, so a gap is read in whole refreshes: a share taken from the raw numbers read 23 %, either side of the limit by chance, as a gap of three refreshes is 49.9 or 50.1 ms. Play counts a frame not presented less than 50 ms after the last, so a gap of exactly that is slow. So at 60 Hz, where nothing lands between 33.3 and 50 ms, the two bars are one, and a surface at 25 frames a second is a slow session at 20 FPS, as two gaps in five are 50 ms.

**Memory by process state.** `perf_snapshot` with `also: anonMemory` reads the state the process is in and keeps the number under it, so a flow that goes home, or a foreground service, fills the other states. Play judges the P90 of its fleet from February 2027: a reading is one device's, and the answer says so.

**Battery signals.** `perf_snapshot` with `also: battery`, over `batteryWindowMs` (30 s by default). Batterystats counts wake locks on battery only, and a phone on a cable never is; telling it otherwise with `dumpsys battery unplug` is what can reset its history. So a lock is read as it is held, once a second, and its age is what `ACQ` says; one held for under a second may not be seen, and the answer says so. Alarms and jobs are counts that go on whatever the power source. A force-stop clears an app's alarm counts: a window with one in it reads from zero. What the system holds for the app's audio or location is listed and marked exempt, from the parser's tests: no device run has held one.

How this was checked, and on which devices: [the evidence](perf-evidence.md#against-plays-definitions).

## Thresholds the tools name

| issue         | threshold                                                                                     | source                 |
| ------------- | --------------------------------------------------------------------------------------------- | ---------------------- |
| jank          | median janky share of the scroll rounds (rounds under 60 frames left out) above 10 %          | this project's default |
| memory growth | over 30 % from the second round's end to the last's (the first round loads images and caches) | this project's default |

`perf_scroll` reads one round, and three where it keeps the run under a `scenario`, for the median a baseline or a
compare takes; `repeats` asks for others. Over the jank threshold it scrolls once more under the CPU profiler, which no
round counts, and names the app's top function in that scroll: on an API 34 emulator, the fixture's heavy list read 94.4 % janky in one round and named `dev.appdyno.fixture.HeavyListActivity.heavyFrame`, 84 % of the samples, in 25 s.

An emulator's numbers depend on the host's load and GPU mode: they are relative and only compared with
the same kind of device (the tools say "virtual device: relative, compare only with the same kind of device").

## Speed

Run it yourself: `node scripts/speed.mjs <device id> [runs]` times the calls an MCP client makes most, on the fixture app (`dev.appdyno.fixture`, from `android/fixture` or `ios/`), on any device. `pnpm build` first. Each run starts a new server over stdio, as a client does, sends `initialize` and `tools/list`, then the calls below. Every call is proved by its answer: a tap has to reach the next screen, a typed field has to hold the text, and a refusal or a missing proof stops the run. The fixture is stopped before each `launch_app`, so each launch is cold. A run before the measured ones starts what the device needs, the iOS runner's build and start or the Android agent's, and only its first read is kept. At the end the script stops the iOS runner it started and waits for it to end, as xcodebuild writes the session's results into the script's state folder as it ends, and then removes that folder.

Medians and the worst of 5 runs, in ms, each through the MCP server over stdio, on 2026-11-10 (the iPhone and the Samsung on 2026-11-09, the Xiaomi on 2026-11-07), on an M5 Pro with 15 cores and macOS 27.0.1, with the commit and the host's load beside each device. A tap or a swipe is timed two ways. The touch alone, with `read: none`, answers once the touch has gone, with no settle and no read, and proves nothing by itself: the script proves it by a wait after it, not timed. With the settled screen, the default, the call also waits until the screen has been still for 200 ms and answers with what changed, which is its proof.
